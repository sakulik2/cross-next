# cross-next

用笔记本（或手机）的浏览器，遥控另一台 Windows 机器上的 QQ音乐。

起因很简单：手上的笔记本音响很烂，台式机音响没那么烂。想在笔记本上切台式机正在播的歌，
又不想为这点事架一套远程桌面。

台式机跑一个 300 KB 的 exe，笔记本什么都不用装，打开网页就是遥控器。

```
笔记本浏览器 ──HTTP/JSON──▶ 台式机 cross-next.exe
（零安装）                    ├─ 媒体线程（MTA 单元）
                              │    ├─ SMTC      → QQ音乐 的播放控制
                              │    └─ Core Audio → QQ音乐 的进程音量
                              └─ HTTP 线程（内嵌网页 + JSON API）
```

## 能做什么

- 上一首 / 下一首 / 播放暂停
- 曲名、歌手、专辑、封面
- 单独调 QQ音乐 的音量和静音（不动系统总音量）
- 封面主色会染成背景渐变，所以界面跟着歌变脸
- 手机上可以「添加到主屏幕」当 App 用

## 不能做什么

这几条不是没做，是做不到，原因写在下面：

- **不能搜索或点播指定歌曲。** SMTC 只提供传输控制和文本元数据，拿不到歌曲 ID。
- **没有播放队列。** 同上，SMTC 不暴露列表。
- **没有歌词。** SMTC 不提供。
- **没有进度条。** 这条是「暂未实现」而非做不到 —— 早期实测碰上 `EndTime` 恒为 0、
  `IsPlaybackPositionEnabled=false`，据此砍掉了进度 UI；后来发现那是「刚打开还没真正
  播放」时的状态，正常播放中时间轴是会上报的。要加的话 `GetTimelineProperties()`
  和 `TryChangePlaybackPositionAsync()` 都可用，但 `mediakey` 模式下仍然没有。

## 五个产物，分别放哪

| 文件 | 放哪台机器 | 用途 |
|---|---|---|
| `cross-next.exe` | **放音乐的那台** | 服务端，必需 |
| `listen.exe` | 鼠标接的那台 | 常驻，抢媒体键转发（驱动没有「启动程序」时用） |
| `remote.exe` | 鼠标接的那台 | 一次性命令，绑到驱动的「启动程序」 |
| `probe.exe` | 放音乐的那台 | 排查 SMTC / 音频会话，可选 |
| `keyprobe.exe` | 鼠标接的那台 | 排查按键走哪条通路，可选 |

只想用浏览器遥控的话，只需要 `cross-next.exe` 一个文件 —— 网页已经编进 exe 里了。

## 跑起来

台式机上：

```sh
cargo build --release
./target/release/cross-next.exe
```

首次运行会在 exe 同目录生成 `config.json` 并打印访问地址：

```
  在笔记本或手机浏览器打开：
    http://192.168.1.1:8770/?t=<32字节随机token>
```

把这个链接在笔记本上打开一次即可 —— 前端会把 token 存进 localStorage，
之后直接访问 `http://192.168.1.1:8770/` 就行。

### 两种控制通路，自动选

QQ音乐 不同版本接入系统媒体框架的方式不一样，所以 cross-next 会自己探测：

| 模式 | 条件 | 能力 |
|---|---|---|
| `smtc` | QQ音乐 注册了 SMTC 会话 | 定向控制 + 曲名/歌手/专辑/封面 |
| `mediakey` | 没有 SMTC 会话，但 QQ音乐 在出声 | 只能发全局媒体键，**没有任何曲目信息** |

实测过的情形：同样都是较新版本，一台机器上 QQ音乐 注册了 SMTC（元数据、封面、
时间轴全都有），另一台完全不注册，只响应老的 `WM_APPCOMMAND` 通路 ——
后者的表现就是键盘媒体键能用，但 `GetSessions()` 返回空。

`mediakey` 模式有两个真实缺陷，界面上会明确提示，不会假装正常：

- **按键是全局的，不针对 QQ音乐。** 系统决定投给谁，所以如果同时有浏览器在放视频，
  可能被它抢走。`smtc` 模式是定向的，没这个问题。
- **读不到任何元数据。** 曲名、封面、播放状态都没有。

音量控制两种模式下都正常 —— 它走 Core Audio，和 SMTC 无关。

如果目标应用以管理员身份运行，UIPI 会拦掉普通权限进程注入的按键。
那种情况下 cross-next 也需要以管理员身份运行。

## 首次配置

`target` 默认 `qqmusic`，按不区分大小写的子串去匹配 SMTC 的 AUMID 和进程名。
正常情况下不用改。要确认实际取值，用附带的探针：

```sh
cargo run --bin probe
```

它先判定当前是不是交互桌面会话（这是「一个会话都没有」最常见的成因），再把所有
SMTC 会话的 AUMID、曲目、能力位、时间轴，以及所有音频会话的进程名打印出来。
跑完停住等回车，所以双击运行也看得到输出。

服务端跑起来之后也可以访问 `/api/sessions?t=<token>` 看同样的会话列表。

**如果一个 SMTC 会话都没有**，用浏览器放个视频再跑一次探针，这一步能一刀切开：
浏览器出现在列表里说明 SMTC 框架正常、是 QQ音乐 没注册（会自动降级到 `mediakey`
模式）；还是空的则是系统层面的问题。

`config.json`：

| 字段 | 说明 |
|---|---|
| `target` | 匹配 AUMID / 进程名的子串，不区分大小写 |
| `port` | 监听端口，默认 8770 |
| `bind` | 留空则自动挑一个内网 IPv4；选错了就写死（见下） |
| `token` | 首次启动自动生成，清空会重新生成 |

## 用鼠标侧键切歌

两种方式，取决于你的鼠标驱动给不给绑「启动程序」。

### 驱动支持「启动程序」：用 remote.exe

一次性客户端，发一条命令就退出，不常驻。侧键绑到「启动程序」，参数填命令名：

```
remote.exe next          下一首
remote.exe prev          上一首
remote.exe playpause     播放/暂停
remote.exe vol +10       音量加 10 个百分点
remote.exe vol 60        音量设为 60%
remote.exe mute          静音开关
```

编译成窗口子系统程序，所以按下去不会闪黑框；从命令行跑时会附加到父进程控制台，
所以配置阶段能看到错误输出，双击运行才弹消息框。实测一条命令约 55ms。

这条路更可靠 —— 完全绕开了「驱动到底发什么键码」的不确定性。

### 驱动只能绑预设媒体键：用 listen.exe

有些驱动只有固定的功能列表（上一首/下一首/音量±…），没有「启动程序」这一项。
这时在**鼠标所在的那台机器**上常驻 `listen.exe`：它用 `RegisterHotKey` 抢下媒体键，
收到就转发给另一台机器。

```
listen.exe        双击或命令行启动，常驻
```

启动后媒体键**只控制远端**，本机播放器收不到 —— 正是"笔记本音响烂、只想控制台式机"
这个场景想要的。关掉程序即恢复。要开机自启就把快捷方式放进 `shell:startup`。

用 `RegisterHotKey` 而不是键盘钩子：它天然独占按键，而钩子只能旁听，
要拦截得返回非零值，那会影响全系统的按键处理。转发在独立线程做，连按不丢键。

如果启动时报「媒体键全部注册失败」，说明有别的程序占着这些键
（另一个 listen.exe、或某个播放器的全局热键），关掉它再试。

### 不确定驱动发的是什么：用 keyprobe.exe

`keyprobe.exe` 同时挂三条通路，按一下侧键就知道驱动走的是哪条：

```
[1] 键盘钩子 捕获: 下一首 (VK_MEDIA_NEXT_TRACK)     标准键盘事件 → listen.exe 可用
[2] Shell 钩子 捕获: 下一首 (APPCOMMAND_...)        WM_APPCOMMAND → 需要另写截获
[3] 系统热键 触发: 下一首                           RegisterHotKey 能独占 → listen.exe 可用
```

注意它运行期间也会独占媒体键（这正是要验证的能力），退出即恢复。

### 别的设备连不上？可能是挑错了网卡

装了 WSL2 或 Hyper-V 的机器上有虚拟网卡，地址通常是 `172.x`。按 RFC1918 算它也是
"私网地址"，但那是宿主机内部的虚拟网段，局域网里的其它设备没有到它的路由 ——
绑上去以后别的机器根本连不上。

自动挑选会优先选**有默认网关**的网卡（虚拟网卡通常没有），所以正常情况下不会选错。
如果还是选错了，跑 `ipconfig` 找到和路由器同网段的那个地址（一般是 `192.168.x.x`），
填进 `config.json` 的 `bind`，重启即可。`bind` 非空时不走自动挑选。

## 必须在桌面会话里运行

不能做成 Windows 服务，也不能从 SSH 启动。

SMTC 会话按 Windows 登录会话隔离。非交互会话里 `GetSessions()` 返回空，
Win11 上 `RequestAsync()` 直接抛 `0x80070424`。

要开机自启，把快捷方式放进 `shell:startup`，或者注册一个
「仅在用户登录时运行」的计划任务。

## 安全边界

这是**明文 HTTP**，token 会出现在内网流量里。

这个取舍对「家里局域网切歌」是合适的 —— 它要挡的是同网段其他设备或程序的
误触和乱按，不是抵御网络嗅探。另外默认只绑到内网 IPv4，不绑 `0.0.0.0`，
所以虚拟网卡、VPN、公网网卡上不会监听。

**不要把这个端口转发到公网。**

## API

除 `/` 以外都需要 token，走 `Authorization: Bearer <token>` 或 `?t=<token>`。

| 路由 | 说明 |
|---|---|
| `GET /` | 内嵌的前端页面 |
| `GET /api/state` | 当前曲目、播放状态、音量、控制模式 |
| `POST /api/cmd` | `{"action":"next"\|"prev"\|"playpause"}` |
| `POST /api/volume` | `{"level":0.0-1.0}` 或 `{"mute":true}` |
| `GET /api/thumbnail` | 封面字节；ETag 是内容哈希。`mediakey` 模式下恒 404 |
| `GET /api/sessions` | 所有 SMTC 会话，排查用 |

`/api/state` 的几个字段值得说明：

- `"mode"` 是 `smtc` / `mediakey` / `none`，即上面那张表里的控制通路。
  前端据此决定要不要显示降级提示。
- `"volume": null` 表示 QQ音乐 当前没有音频会话。Core Audio 只列出活跃过的会话，
  QQ音乐 没实际出声时列表里根本没有它。前端据此把滑杆置灰，而不是显示 0。
- `"matched"` 为 false 表示没匹配到 `target`，当前控制的是系统的「当前会话」，
  具体是谁看 `aumid`。
- `"artTag"` 是曲目元数据的哈希，换歌才变。前端用它判断要不要重取封面。

命令类接口返回 `{"accepted": bool}`。`false` 表示 QQ音乐 拒绝了这条命令 ——
这不是错误，如实回传，前端会提示「未接受」而不是假装成功。

## 实现上的几个决定

**为什么没有依赖。** 只依赖 `windows` crate（WinRT/Win32 绑定）。HTTP 是手写的
——只需要伺候一个自家前端，为此引入 axum 会连带 tokio 一整套。JSON 也是手写的，
字段固定且很少。这也延续了这个仓库其它项目的取向。

**为什么有个专门的媒体线程。** 它独占一个 MTA 单元并持有 `SessionManager`。
这样 COM 单元只初始化一次，WinRT 对象不用跨线程传递，也满足 windows-rs
[#2061](https://github.com/microsoft/windows-rs/issues/2061) 的建议
——复用同一个 manager 实例，反复创建会漏内存。

**为什么不查能力位。** 实测 QQ音乐 上报不完整：状态是 `Opened` 时
`IsPauseEnabled=false`，照能力位禁用按钮会让播放键一直灰着。所以直接发
`TryTogglePlayPauseAsync`，让应用自己拒绝，把 `accepted` 如实回传。

**为什么音量每次都重新枚举。** 见上面 `"volume": null` 那条 —— 音频会话是动态的，
启动时缓存一次会在 QQ音乐 重新出声后失效。

**`block_on` 是自己写的。** windows-future 0.3 只公开了 `IntoFuture`，
阻塞用的 `Async` trait 是私有的。媒体线程本来就是同步的，为此引入
async 运行时不划算，所以用 `SetCompleted` + `Condvar` 写了一个（`src/winrt_block.rs`）。
它必须在 MTA 线程上调用 —— STA 上阻塞等待会因为缺消息泵而死锁。
